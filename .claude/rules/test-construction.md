# Test Construction, Determinism & E2E Runtime Discipline

**MANDATORY whenever tests are written or modified (every story / bug).** `testing.md` defines WHAT to test (matrix, coverage floors, E2E existence, integrity); this rule defines HOW to build tests that stay trustworthy: structure, isolation, determinism, and E2E runtime behavior.

---

## §1 Construction Standards

- **AAA structure** — Arrange / Act / Assert, in that order, visually separated. No assertions inside the arrange block.
- **One behavior per `it()`** — a test that asserts two behaviors hides which one broke. Split it.
- **No order-dependence** — every test creates its own data (factories/helpers) and never relies on state left by a previous test. The suite MUST pass with any test run alone (`-t`) and in any order.
- **Factories over fixtures** — shared test data comes from factory functions with overridable fields (`makeUser({ role: 'ADMIN' })`), never from module-level mutable objects that tests mutate in place.
- **DB isolation** — integration tests run each test in a rolled-back transaction OR truncate affected tables in `beforeEach`. Pick ONE strategy per project and record it in `.project-management/rules/project-rules.md`.
- **Deterministic seed** — a `db:seed:test` script creates the baseline data (roles, enums, one user per role) identically on every run. It is part of the E2E setup contract (`commands/modules/e2e-setup.md`).

---

## §2 Determinism & Flaky Policy

- **Tests control time and randomness:** fake timers / injected clock (never assert against real `Date.now()` drift); seeded random (fixed faker seed). A test that passes only at certain speeds or times is broken.
- **Zero retries locally.** CI MAY allow at most 1 retry, but **a retried pass is a flaky FAIL for quality purposes**: log it in `output/progress/blockers.md` the same day and quarantine-or-fix — a flake left in place trains everyone to re-run until green.
- **Never widen a timeout to make a test pass** — find the unresolved promise / missing await instead. Timeout bumps require the same justification discipline as `.skip` (`testing.md` Test Integrity).
- **Playwright config guards** (generated by `e2e-setup.md`): `forbidOnly: true` (CI fails on a committed `.only` — mechanical backstop for the Integrity gate) and `fullyParallel: true` (parallel-safe tests are order-independent tests; failures under parallelism are isolation bugs, not reasons to serialize).

---

## §3 E2E Runtime Discipline

- **No sleeps.** `page.waitForTimeout()` / manual sleeps are forbidden in E2E code. Use condition-based waits and web-first assertions (`await expect(locator).toBeVisible()` auto-retries). Selector policy stays testid-first per `frontend-test-identifiers.md` §4.
- **Dedicated test environment:** E2E runs against a test DB/env booted with the deterministic seed — never against a developer's dirty local data. `playwright.config.ts` `webServer.command` points at the test-env start (`e2e-setup.md`).
- **Each scenario owns its data:** create or reset what the scenario needs via API/seed helpers in `beforeEach` — never depend on leftovers from another scenario (that is order-dependence, §1).
- **Stubbing policy:**
  - **First-party (your app's own API/services): NEVER stubbed in E2E.** Stubbing your own backend turns the E2E suite into an expensive component test — the whole point is the real wiring.
  - **Third-party at the process boundary (payments, email, external OAuth): stubbed by default** (`page.route` / sandbox mode / mail-catcher). Real third-party calls are opt-in per project, never a hidden dependency of the suite.
- **Flutter (default mobile stack) — same discipline, Flutter idiom:** E2E = `integration_test` on device/emulator via `run_e2e.sh fake|live|all`. No sleeps → `await tester.pumpAndSettle()` / condition-based `pumpUntil` helpers, never `Future.delayed`. Selectors `find.byKey`-first (`frontend-test-identifiers.md` §4). Fake mode (`support/fake_app.dart`) is the third-party/backend boundary stub; live mode runs against the seeded test backend (first-party never stubbed there).

## §4 Concurrency Tests — Deliberate Races Are NOT Flakes

**Required whenever a story adds/changes a DB-enforced invariant, guarded state transition, rate limiter, an optimistic-locked record, or an idempotency key** (`.claude/rules/database.md` — Invariants Live in the Database; `.claude/rules/background-work.md` §3; `.claude/rules/concurrency-control.md` §5).

- **Pattern:** fire N identical calls concurrently (`await Promise.all([...])` at the service or request level), then assert the **invariant in the DB** — exactly one open version exists, exactly one row inserted, at most `max` attempts passed the limiter, the token was consumed exactly once. The others must fail with the domain conflict error, not corrupt state.
- **Carve-out from §2:** the §2 ban targets *timing-dependent* tests (asserting real-clock behavior, sleeps, speed-sensitive passes). A deliberate concurrent invocation asserting a DB invariant is **deterministic in outcome** — regardless of interleaving, the invariant must hold — so it is required, not forbidden. Do NOT add sleeps to "shape" the race; the constraint/lock must win every interleaving.
- **The sequential test is not a substitute:** "calling it twice doesn't duplicate" proves the single-threaded path only. Keep it, but the concurrent variant is what proves the constraint/lock (`database.md`).
- **DB isolation still applies (§1):** run concurrency tests against the real test DB (a mocked DB cannot race); the truncate/rollback strategy must reset all rows the N calls created.

## Enforcement

- `/execute-work` quality gates reference this rule from the Testing checklist (`commands/modules/execute-work-quality-gates-core.md`); §2 violations surface via the Integrity grep + results block (`testing.md`).
- `e2e-setup.md` generates the §2 config guards and the §3 test-env wiring for new projects.
- The optional per-project `.project-management/rules/TESTING-RULES.md` records the project's §1 DB-isolation strategy and seed command; its flaky-test troubleshooting section follows §2 (waits, not retries).
