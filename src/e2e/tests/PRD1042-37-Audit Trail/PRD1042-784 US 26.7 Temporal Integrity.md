@audit @temporal-integrity @us-26.7 @p0
Feature: Temporal Integrity & Immutable Timestamp Enforcement (US 26.7 — PRD1042-784)
  As an Auditor
  I want all audit timestamps to be server-assigned immutable UTC values
  So that event sequence is deterministically reconstructable and client clocks cannot distort the evidence record

  Background:
    Given the audit trail service is operational
    And the server clock is synchronized via the platform's authoritative time source
    And an authorized actor exists for each role in scope

  # ---------------------------------------------------------------------------
  # HAPPY PATH — AC-01
  # Any auditable action must persist a record whose timestamp field is a
  # server-assigned ISO 8601 UTC value populated at persistence time.
  # Verifies the CC-1 §6.1 contract: timestamp is mandatory and server-owned.
  # ---------------------------------------------------------------------------

  @happy-path @ac-01 @p0
  Scenario: Server assigns UTC timestamp on audit record creation (AC-01)
    Given I am authenticated as "system_admin"
    And no client-supplied timestamp is included in the request payload
    When I perform an auditable action that emits an audit record
    Then the persisted audit record contains a "timestamp" field
    And the "timestamp" value is a valid ISO 8601 datetime in UTC
    And the "timestamp" value is within 5 seconds of the server's current UTC time
    And the "timestamp" is populated with the server value regardless of the client's local timezone

  # ---------------------------------------------------------------------------
  # HAPPY PATH — AC-03
  # Two audit events emitted for the same business entity must have a
  # deterministic order — established by chainSequence (per story) or the
  # audit_seq IDENTITY column (per Marko Mrdja BE alignment 2026-06-18).
  # Test at behaviour level: given two consecutive events on the same entity,
  # the second one always ranks after the first even if server timestamps
  # collide down to the millisecond.
  # ---------------------------------------------------------------------------

  @happy-path @ac-03 @p0
  Scenario: Same-entity events retain deterministic ordering via chainSequence (AC-03)
    Given I am authenticated as "system_admin"
    And a business entity "ENT-001" exists
    When two audit-emitting actions execute against "ENT-001" in immediate succession
    Then two audit records exist for entity "ENT-001"
    And the two records have distinct disambiguation-sequence values
    And when the two records are queried by natural ordering, the second action's record follows the first
    And the ordering is stable across repeated queries of the same window

  # ---------------------------------------------------------------------------
  # MAIN ERROR — AC-02, AC-07
  # The RefiNext security domain rule "no caller-supplied timestamp may be
  # persisted" applies to every role and every endpoint. If a client tries to
  # backdate or forward-date an audit event by including a "timestamp" (or an
  # alias — recorded_at, created_at, event_time) in the request payload, the
  # server must ignore the client value and write the server-side UTC value.
  # ---------------------------------------------------------------------------

  @main-error @ac-02 @ac-07 @p0
  Scenario Outline: Client-supplied timestamp is ignored, server value overrides (AC-02, AC-07)
    Given I am authenticated as <role>
    And I submit an auditable action whose payload contains a client-supplied "<field>" set to "2020-01-01T00:00:00Z"
    When the audit record is persisted
    Then the persisted "timestamp" is NOT "2020-01-01T00:00:00Z"
    And the persisted "timestamp" is the server-assigned UTC value at persistence time
    And no field named "<field>" is echoed back with the client value

    Examples:
      | role          | field       |
      | system_admin  | timestamp   |
      | front_office  | recorded_at |
      | back_office   | event_time  |

  # ---------------------------------------------------------------------------
  # MAIN ERROR — AC-04
  # Timestamp immutability is enforced by the INSERT-only permission model
  # (US 26.03). Any attempt to UPDATE or DELETE an audit record via the DB
  # role available to the application service account must be rejected, and
  # no alternate endpoint may exist that would rewrite the timestamp field.
  # ---------------------------------------------------------------------------

  @main-error @ac-04 @p0
  Scenario: Timestamp is immutable — UPDATE / DELETE on persisted audit record rejected (AC-04)
    Given I am authenticated as "system_admin"
    And an audit record exists for entity "ENT-001" with a persisted "timestamp"
    And I capture the original "timestamp" value as <original_ts>
    When I attempt via any admin surface to modify the "timestamp" field of that audit record
    Then the modification attempt is rejected
    And when I re-query the audit record, its "timestamp" still equals <original_ts>
    When I attempt via any admin surface to delete the same audit record
    Then the delete attempt is rejected
    And the audit record still exists with "timestamp" equal to <original_ts>

  # ---------------------------------------------------------------------------
  # MAIN ERROR — AC-11 (RBAC — auto-applied by RefiNext role-access domain)
  # Per Permission Matrix, only System / Power User "assigns" timestamps and
  # even that assignment is system-driven (server-side). No role — including
  # System Admin, and explicitly excluding Auditor / FO / BO / Support / LC User
  # — may provide or override a timestamp from the client. The rejection is
  # uniform across roles: server value wins.
  # ---------------------------------------------------------------------------

  @main-error @ac-11 @rbac @p0
  Scenario Outline: RBAC — every role cannot override server timestamp (AC-11)
    Given I am authenticated as <role>
    And I submit an auditable action whose payload includes a client-supplied "timestamp" of "1999-12-31T23:59:59Z"
    When the audit record is persisted
    Then the persisted "timestamp" is NOT "1999-12-31T23:59:59Z"
    And the persisted "timestamp" is the server-assigned UTC value
    And the actor recorded on the audit record equals <role>

    Examples:
      | role                 |
      | system_admin         |
      | auditor              |
      | front_office         |
      | back_office          |
      | support_user         |
      | leasing_company_user |
